# Broker architectural context

## When To Read This / Authority

Read this for daemon PTY lifecycle, attach/replay ordering, snapshot performance, terminal semantics, program-status handling, or native-build changes. Application HTTP authorization, viewer ownership, browser hydration/credit, reconnect policy, and service/pair installation belong to the sibling `wolfpack` context; consult that document only when crossing those boundaries. This daemon does not implement those application policies.

The broker owns session UUIDs, child processes/PTYS, canonical terminal state, output watermarks, bounded replay, and connection-local subscriptions. Native Ghostty supplies terminal semantics through a checked C shim; Rust retains resource lifetime, sequencing, status records, and wire authority. State is in memory, not restart-restored session storage. Socket-client disconnect does not kill a session. `Server::shutdown` stops acceptance and signals connection tasks, then removes the pathname; it neither explicitly kills all children nor joins every connection/session thread. Do not infer process-tree shutdown guarantees from that API (`src/server.rs:145–224,287–468`; binary startup/shutdown: `src/bin/wolfpack-broker.rs:16–60`).

The sibling staged context was used for application-side boundary descriptions only; no sibling source bodies were read. Its TypeScript broker client/backend/renderer and terminal-theme pointers are conditional companion reads for wire, attach, or palette changes.

## Trust and execution boundary

- Unix-socket access is the daemon's privilege boundary, not a second JWT/user/session authorization layer. A connected client can create commands with caller-supplied argv, cwd and environment, signal recorded PIDs, and write terminal input by UUID. The broker does not impose the application's project containment or command-selection policy. Process launch uses `CommandBuilder` argv rather than introducing shell parsing itself; a caller may deliberately launch a shell. The broker overrides any supplied `WOLFPACK_SESSION_ID` with its own new UUID (`src/session_router.rs:130–224`; `src/session.rs:261–345,487–517`).
- Startup validates effective ownership and lack of group/other write permission on the immediate socket parent, preserves safe existing directory permissions, refuses non-socket replacement, probes an existing socket before removing a stale one, and creates the socket under a temporary owner-only umask. That umask is process-global, so its guard serializes broker bind operations and restores the previous value; it is not a general synchronization mechanism for unrelated file creation. Exact path selection and filesystem rules: `src/server.rs:99–122,166–285`; daemon environment override: `src/bin/wolfpack-broker.rs:23–25`.
- The codec validates frame kind/length before inbound payload allocation and deserializes typed envelopes. Wrong-direction frames or malformed framing/JSON terminate that connection; method/parameter errors normally return protocol errors. Dimension/reflow-width checks are router/server boundary checks, not universal guarantees of the public `Session`/terminal library APIs. Unknown-session input is ignored; stdin write failures are logged rather than acknowledged as RPC success/failure (`src/codec.rs:20–49,129–153,201–236`; `src/server.rs:373–388,562–579`; `src/session_router.rs:280–304`).
- Wire compatibility spans the sibling adapter. Exact frame layout, per-kind budgets and endian rules live in `src/codec.rs`; serde shapes/defaults, method names and error/event variants live in `src/protocol.rs`. Binary sequences are full-width integers, while lightweight session/output-exit metadata uses decimal strings. `PROTOCOL_VERSION` is contract/log metadata here, not a negotiated connection handshake. Avoid turning these into ordinary JavaScript-number counters across the boundary.

## Session lifetime and registry ownership

Creation reserves a name under the registry mutex, releases that mutex for PTY/process/thread setup, and commits the live UUID afterward. Concurrent creators therefore see an occupied name without globally serializing spawn. Setup failure removes only its matching reservation. A child guard kills and waits on the child if post-spawn setup fails; successful reaper-thread ownership disarms that rollback. The slave is dropped after launch so the daemon does not pin its descriptor (`src/registry.rs:141–192`; `src/session.rs:165–208,261–430`; rollback tests: `every_post_spawn_setup_failure_kills_and_reaps_the_child`).

**Names are reusable; UUIDs identify an incarnation.** The registry reaper removes an exited session from the live table/name map but retains a bounded, expiring by-ID tombstone for terminal inspection/final replay. Thus `get(id)` and `list()` intentionally have different visibility, and a recreated name can coexist with an older UUID's retained output. Heavy session graphs are released outside the registry mutex. Expiry is both lazy and timer-maintained; due maintenance has priority over event traffic. Lost exit events trigger an authoritative dead-session sweep, not blind reliance on later events for that UUID. Library harnesses must explicitly start `spawn_exit_reaper` if they expect production name release/tombstone maintenance (`src/registry.rs:61–115,195–310`; TTL/cap/cadence authority at its constants).

Child exit and output completion are separate transitions. The child waiter first waits for output-bus closure; on its bounded drain timeout it closes the bus while holding the terminal lock. The drainer checks closure under that same lock before feeding more bytes, freezing terminal truth and the final watermark after forced closure. Normal exit then drops transient status, flushes its pending status event, records exit, and emits one exit transition. A read/feed failure closes output, marks the session unavailable, emits an exit with the current watermark, and attempts child termination; later wait completion records the exit code without duplicating that lifecycle event. `alive=false` is therefore not universally proof that child waiting has completed (`src/session.rs:1324–1428,1502–1555`).

An exit event's final watermark covers published output, **not socket delivery**. Lifecycle events use the control queue and can overtake terminal output. Consumers must drain according to watermarks rather than treating receipt of `session_exited` as delivery of all preceding bytes.

## The two attach barriers

There are two distinct cuts; preserving only one is insufficient.

1. **Terminal/replay cut.** The drainer feeds a chunk, increments its sequence, and publishes that chunk while holding the terminal mutex. Snapshot capture reads terminal state and sequence and installs its bus subscription under the same terminal→bus lock ordering. The bus itself serializes publication and replay/live receiver creation using sender→ring ordering. A successful atomic cut therefore has `snapshot.seq == subscription.current_seq`; subsequent output is on the receiver, never silently between snapshot and attach (`src/session.rs:577–604,1334–1397`; `src/output_bus.rs:113–161`).
2. **Socket-write cut.** Queue insertion is not a response-ordering barrier because output and control have separate queues and the writer deliberately yields to output after bounded control bursts. Attach forwarders wait for a private acknowledgement sent only after the response frame is successfully written/flushed. Dropped acknowledgement releases no associated output. The dispatcher does not await that acknowledgement: the subscription map owns the waiting task so unsubscribe/replacement/shutdown can abort it (`src/server.rs:77–96,510–558,734–901,1069–1088`; tests around `snapshot_subscribe_response_write_precedes_associated_output_after_control_burst`).

Snapshot-subscribe methods build a provisional capture off-runtime before replacing an existing subscription. Capture/render failure leaves the previous subscription untouched. Successful replacement aborts the old forwarder; unsubscribe is idempotent but cannot retract already queued/in-flight frames. Connection cancellation drops the subscription owner and aborts all forwarders, including those awaiting their response boundary. Already-running `spawn_blocking` work can finish after cancellation, but its result is discarded. Snapshot admission permits are acquired **inside** that blocking work so cancellation does not prematurely release capacity (`src/server.rs:581–623,734–940`).

Ordinary `subscribe` atomically combines ring replay and a receiver, not terminal snapshot state. Replay is strictly after the requested watermark; omitted watermark means live-only. `replay_truncated` means the retained ring cannot cover the requested gap, not a successful complete replay. A closed bus can still replay its retained window and supplies an already-closed live receiver (`src/output_bus.rs:131–161`; ring eviction: `src/ring_buffer.rs:55–75`).

## Backpressure, ordering, and snapshot cost

- One ordered control worker per connection preserves control operation/response order; expensive router/snapshot work runs through blocking tasks. Input has a separate bounded FIFO worker so snapshot computation does not inherently serialize keyboard input. This is not a global input/control transaction order: queue saturation still backpressures the shared socket reader, and PTY writes themselves are synchronous/blocking (`src/server.rs:342–468,581–623`).
- Control/global events and output have separate bounded writer queues, with control priority and bounded fairness. Event reception is attached synchronously at accept time to avoid a scheduling gap before the event forwarder starts. Global event lag is best-effort/log-and-continue, unlike output-subscription lag recovery (`src/server.rs:287–340,470–487,510–558`).
- Output forwarders keep a byte-bounded local FIFO while the socket writer is blocked. Adjacent sequence chunks may be coalesced, preserving byte order but reporting the **last included chunk's sequence**. Sequences are watermarks, not frame counts or byte offsets. Fanout/replay normally share immutable byte allocations; coalescing uses copy-on-write. Once broadcast lag occurs, the forwarder stops and queues a subscription-dropped event behind already accepted output on the **output** queue. Unaccepted local pending bytes need replay recovery; this event must not be moved to the prioritized global-event path (`src/server.rs:942–1063`). Exact queue/connection/subscription budgets are the constants at the top of `server.rs`; retention limits are in `output_bus.rs`/`ring_buffer.rs`, not one global memory cap.
- Snapshot capture copies bounded native arrays/text under the terminal lock, then releases it before styled allocation and scrollback reflow. No native pointer survives capture. Each session caches one immutable materialized snapshot keyed by sequence and request options; hits share an `Arc`, including the earlier capture timestamp. Resize changes truth without advancing output sequence, so successful resize invalidates the cache and increments a separate generation; in-flight old materialization may still return its valid earlier capture but cannot repopulate that invalidated cache. New output likewise prevents stale cache insertion (`src/session.rs:553–640`; regression tests at `2335–2482`).
- Snapshot admission is registry-wide, shared across standalone and atomic-attach methods, not per connection. Production uses one registry. Permits cover capture/materialization/attach rendering, not later writer serialization (`src/registry.rs:49–59,117–139`; `src/session_router.rs:226–248`; `src/server.rs:773–789`).
- Resize serializes through master→session-state→terminal, attempts terminal resize before PTY resize, rolls terminal geometry back on PTY failure, and commits metadata/cache invalidation/success events only after success. Rollback failure has its own error path; do not assume every failed resize leaves native terminal state unchanged (`src/session.rs:521–539,682–722`).

## Native semantics and status side effects

The FFI handle has one Rust owner and one destructor; its `Send` assertion relies on serialized per-session access, not thread-safe native internals. Callback sinks point to stack-owned Rust collectors only during synchronous feed and are cleared before returning. Shim-owned selector/status values are explicitly translated rather than cast from upstream enums. Row/text/cell allocation, coordinate arithmetic and native text ranges are bounded/checked on the respective sides (`src/terminal_state.rs:76–440,481–562,755–803`; `native/ghostty_vt_shim.{h,c}`; arithmetic helpers: `native/ghostty_vt_internal.h`). Upstream parsing and ABI conformance remain dependency contracts, not independently proven by these checks.

Important semantic boundaries:

- The historically named constructor scrollback limit is passed to Ghostty's **byte-budget** option, not a promised number of retained rows. RPC scrollback limits instead select trailing raw rows before optional reflow. Alternate-screen snapshots intentionally omit primary history; target width reflows scrollback, not visible-screen geometry (`native/ghostty_vt_shim.c:197–206`; `src/terminal_state.rs:643–676,806–865`).
- Native VT feed is a void upstream API wrapped as success; latched semantic-processing error metadata is rejected during snapshot capture. Do not assume every semantic failure surfaces immediately as `try_feed` failure (`native/ghostty_vt_shim.c:248–258`; `src/terminal_state.rs:244–250,691–700`).
- Native initialization disables terminal image storage/external media and the glyph protocol. Palette-indexed colors become RGB in snapshots, so the shim palette must track the application terminal theme; otherwise prefill and live rendering diverge (`native/ghostty_vt_shim.c:97–130`).
- ANSI prefill preserves the entire visible screen and trims only oldest whole history lines. The requested byte budget can therefore be exceeded by visible content; a separate hard prefill ceiling yields the distinct fallback error. ANSI is a projection, not replay of original terminal control traffic or every snapshot field. Full JSON remains richer. Rendering and fallback-size authority: `src/ansi_render.rs:1–247`; `src/server.rs:658–717`; hard limits and response headroom assertions: `src/protocol.rs:387–397`, `src/terminal_state.rs:44–73`. Extraction limits are not interchangeable with final serialized-frame limits.

Program-status text originates in untrusted PTY output. Native parsing reports it; Rust owns sanitized, bounded replacement records, descendant clear semantics, root-protected eviction, and content-change timestamps. Unchanged reports refresh eviction recency without changing the content timestamp. Full records are available through single-session info; lists and paced events expose only the root. Prompt/exit drops transient records but preserves completion/error records. Foreground watching uses the group observed when reports are drained, not authenticated emitter identity; unreadable foreground does not prove departure (`src/program_status.rs:76–236`; `src/session.rs:984–1225`).

Only the fixed program-status capability replies are written back by the broker. Other native query replies are deliberately discarded because the browser terminal answers those queries; forwarding both would duplicate stdin replies. These broker replies never wait behind a client writer on the drainer thread. Whole replies are bounded/best-effort, but a partially written reply's tail must precede later client input to complete its escape sequence. Only the drainer temporarily enables nonblocking mode: duplicated FDs share the open-file-description flags, so moving that operation to another thread can affect a concurrent read. The final PTY writer drop also avoids portable-pty's potentially blocking EOF write (`src/terminal_state.rs:450–492`; `src/session.rs:769–956,1228–1296`).

## Verification routing and evidence limits

Use session unit tests for setup rollback, drain/exit boundaries, blocked-input/query interaction, resize failures and off-lock materialization/cache generations. Use server unit tests for writer fairness, response-written acknowledgements, lag and cancellation. `tests/socket_integration.rs` exercises real socket/PTY ordering and security setup; its lightweight harness does **not** start the registry exit-reaper, unlike the binary. Its ordinary round-trip helper discards incidental events/output, so event-order assertions need the dedicated collectors.

Terminal fixture/stress/FFI and native-helper tests cover extraction, malformed/split input and arithmetic independently of browser behavior. `tests/ansi_render_fixtures.rs` compares against checked-in TypeScript-generated bytes; its ignored regeneration path rewrites fixtures and requires the companion application generator afterward. The isolated memory-budget test is GNU/Linux allocator telemetry, not RSS or tombstone-reclamation evidence, and skips on other targets. Native-link runtime smoke tests guard the archive's interaction with Tokio (`tests/ghostty_static_link.rs`).

Cargo builds require an already verified native bundle. `build.rs:37–201` verifies target, root lock digest/content, archive/header hashes, fixed bundle paths and host-memory-symbol policy before compiling/linking the shim; it does not download/build Ghostty. Bundle preparation, patch provenance and lock authority are application-owned boundaries described in the sibling context. Do not bypass manifest checks or treat browser WASM Ghostty as the daemon dependency. Socket tests require a host environment permitting Unix bind/listen; binary diagnostics explicitly distinguish sandbox permission denial (`src/bin/wolfpack-broker.rs:71–98`).

This pass read production Rust, build logic and the checked C shim/helpers, plus selected regression-test bodies. It did not inspect upstream Ghostty/portable-pty internals, sibling implementation bodies, every test branch, or generated native bundle contents. Existing cached test executables passed output-bus tests (8), codec tests (14), and native arithmetic/selector helper tests (4). They predate this pass and were not rebuilt, so these checks are supporting evidence only, **not current-source acceptance**. No fresh Cargo build, full socket/PTY suite, browser parity regeneration, or platform/memory acceptance run was performed. Octocode's initially partial tree was continued to its final page; exact native source reads, not semantic/graph claims, support this document.
