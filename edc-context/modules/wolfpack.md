# Wolfpack application context

## When To Read This / Authority

Read this before changes spanning terminal attach/reconnect, session identity, selected-machine routing, extension execution, task workers, or distribution. This is a broad application module, not just the HTTP server: it owns the Bun server/CLI, browser control room, TypeScript broker adapter, extension SDK/runtime, and build/install/test integration. For an isolated visual or pure-helper change, use the relevant source and focused tests; the sections below are conditional routing, not a mandatory reading list.

The sibling `broker` module is a separate daemon boundary. Application-side contracts are in `src/server/backend-contract.ts`, `src/server/broker-backend.ts`, and `src/broker/{client,codec,snapshot-render}.ts`. Consult the sibling context/source separately for daemon PTY ownership, native terminal implementation, or wire compatibility changes. No sibling source bodies were inspected here, and no sibling signature/context was available during this pass. Do not infer daemon implementation from application comments or test fixtures.

**Durable authority is deliberately divided:** broker facts supply session UUID/liveness/terminal state; application identity files augment those facts; server reducers own semantic runtime/attention state; extension snapshots/schema stores own extension data; durable tasks and volatile relay have different authorities and recovery models. Browser mounted terminals, labels, cached peers, and persisted workspace preferences are not substitutes for these authorities.

## Startup, exposure, and lifetime boundaries

- `src/cli/index.ts:start` selects managed-service versus foreground startup and applies the service credential file before importing the server. Source execution and packaged execution differ: the npm entry (`bin/run.cjs`) validates an exact-version optional platform package containing **both** executables and runs its server; it intentionally ignores repository `bin/wolfpack`. Service installation stages a stable executable pair rather than running indefinitely out of an npm cache.
- `src/server/index.ts:startServer` verifies auth configuration before binding, initializes the broker router, probes it, initializes durable tasks and the relay worker, then starts observation and listening. A missing broker socket is fatal in the production router constructor; a socket that exists but fails its handshake instead tears down that client and can leave a listening, degraded server awaiting recovery. Do not equate a listening port, socket pathname, or service-manager process status with application readiness. `src/server/operability.ts:operationalHealth` and `src/cli/readiness.ts` require the live broker-ready state; the latter explicitly measures endpoint health, not process identity.
- Broker-only is the supported architecture. Old tmux/in-process-PTY terminology remains in comments, mocks, and compatibility-shaped fields; it does not describe another production fallback. `BackendRouter` (`src/server/backend.ts`) distinguishes availability from connection readiness and has a recovery watchdog. `BrokerClient` owns reconnect/resubscribe; RPCs in flight are rejected on disconnect, not automatically replayed as mutations. Retry decisions belong to callers that understand idempotency. Timeout circuit-breaking addresses a connected-but-nonresponsive daemon, not merely socket disappearance.
- Server restart and broker restart have different consequences. Viewer shutdown (`src/server/shutdown.ts`) announces a restart and bounds close handshakes; it does not destroy broker-owned sessions. Pair replacement/service management (`src/cli/service.ts:installCandidatePair`, `serviceStop`, `serviceRestart`) stops the server before a changed broker and warns before terminating broker-owned sessions. Managed startup requires probe tooling before disruptive actions; foreground readiness uses direct loopback HTTP instead.
- JWT enforcement is conditional, not per-user authorization: absent secret intentionally permits owner API access; an invalid configured secret causes startup refusal. Cached configuration is lazy and remains fixed until reset/restart (`src/auth.ts`). `src/server/index.ts` applies origin policy, auth, and quotas before extension/static route dispatch. Public identity/handshake exceptions and operational-loopback exceptions are authoritative in `src/server/http.ts:shouldAuthenticateApiPath` and `src/server/index.ts`, not a blanket “all API routes require JWT” assumption.
- Default binding is loopback; remote access assumes owner-controlled Tailscale Serve/Tailnet policy. Browser allowed origins derive from the configured canonical hostname, not forwarded headers. Origin recovery for Serve and direct-loopback operational exemptions use different checks (`src/server/tailnet-origin-policy.ts`, `operability.ts`). Quota/ticket identity can be a Serve login rather than a socket IP. These are trusted-local-proxy assumptions, not a general reverse-proxy design.
- Browser credentials are tab-scoped and origin-scoped (`public/browser-auth.ts`). WebSocket upgrade can consume a short-lived, single-use, client-key-bound ticket before falling back to JWT validation. Consumption removes the ticket even on a client-key mismatch (`src/server/ws-ticket.ts`); connection capacity reservations are released on every rejected upgrade and transferred to the accepted socket on success (`src/server/index.ts`).

## Session identity, paths, and mutation ordering

**Names are reusable UI/attach addresses; UUIDs pin an incarnation.** `src/server/session-selector.ts` rejects a selector that simultaneously names one active session and identifies another. `BrokerBackend.list()` returns live names, whereas `listSessionFacts()` restores identity metadata from the complete broker table and projects liveness/output/program-status facts. `inspectSession()` reads broker truth directly, including dead entries, without depending on identity-file timestamps (`src/server/broker-backend.ts:520–617`). An identity sidecar alone proves neither existence nor liveness.

- `SessionIdentityStore` restores by UUID, preserves appropriate metadata, prunes identities absent from the supplied broker table, and redacts external provider IDs only in public projection (`src/server/session-identity.ts`). Memory/private modes and path overrides are there; exact persistence locations belong to that source, not a universal “everything is under the project” assumption.
- Session creation is not one atomic application transaction: broker creation precedes local identity capture; task-worker registration/readiness and child-parent rechecks come later. The UI legacy create route and structured session-create/open routes have different request contracts (`src/server/project-settings-routes.ts`). Directory creation can precede a later launch failure. Do not assume an unsuccessful HTTP response means no external resource was created.
- `createTopLevelSession` and `openSubSession` retry duplicate-name allocation against fresh live names. Child allocation captures a parent UUID and checks for parent replacement across retry and after creation. In `openSubSession`, task-worker failure uses exact-ID cleanup; ordinary child creation does not universally roll back when a later parent check fails. Source truth: `src/server/{session-create,session-open}.ts`.
- Project-name selection is confined under configured `DEV_DIR`, but explicitly selected existing absolute directories intentionally use another validator and need not be under it. Both paths canonicalize and reject a final symlink; do not apply the project-name containment model to explicit-path APIs (`src/server/{project-selection,validate-project-dir,dev-dir}.ts`). Canonical cwd then propagates into broker creation, identity, Git access, worker policy, and readiness.
- Command validation and shell argument separation are complementary. `BrokerBackend.createSession` builds a login-shell command, passes model/prompt as positional arguments, and uses an exec-only Pi task-worker launch; ordinary agent launches can return to an interactive shell. Thus terminal liveness is not the same as the agent still running. Task workers reject incompatible harness/prompt combinations (`src/server/broker-backend.ts:619–737`).
- Prompt-and-observe is distinct from passive wait/capture. `writeObservedInput` registers UUID-pinned output/lifecycle observation, establishes an output sequence boundary, then writes input, and always removes observation resources. Only later output can satisfy prompt matching; older output and replay gaps have explicit outcomes. Send/submission observation has its own status timeline and must not be reduced to “write succeeded means submitted.” Read `src/server/broker-backend.ts:sendAndObserveSubmission`, `promptAndWaitForOutput`, `writeObservedInput` with `src/session-{send,prompt}-contract.ts` and `src/server/session-control-routes.ts`. Non-streaming inspector captures use exact IDs and a separately bounded/coalescing service (`src/server/session-snapshot.ts`).

## Terminal transport: preserve the cuts, not just the bytes

The browser Ghostty instance is a disposable projection of broker terminal state. Attach crosses asynchronous geometry settlement, snapshot capture, stream adoption, input release, resize acknowledgement, and reveal; changing only one side readily breaks ordering.

1. `src/server/websocket.ts:setupNewPtyEntry` acknowledges attach promptly but gates accepted binary input until the replay-capable subscription is live. Full/viewport hydration settles geometry and observes resize-triggered output before snapshotting. The no-prefill path subscribes **before** its initial resize. Attach-finalizer ownership prevents a resize received during snapshot/subscription from simultaneously entering ordinary resize debounce.
2. `BrokerBackend.beginSessionAttach` returns a single-consumer lease: pending → active or cancelled. The preferred cut is broker-rendered ANSI snapshot-plus-subscribe; supported fallback errors select JSON atomic capture, then legacy snapshot-plus-sequence-replay only for older capability support. These are not equivalent byte-budget policies: ANSI can preserve the complete visible screen above the requested budget; the JSON/legacy renderer trims the rendered tail. `src/server/backend-contract.ts:SessionPrefillOptions` documents the distinction; implementation is `src/server/broker-backend.ts:1295–1335,1653–1774`.
3. The caller must activate or cancel every lease. WebSocket attach cancels in `finally`; cancellation after successful adoption is intentionally harmless. Client-side provisional subscription ownership, queued output, deferred unsubscribe, per-session backend refcounts, and replay deduplication together protect overlapping viewers/observers. Do not replace these with a simple snapshot RPC followed by a live listener (`src/broker/client.ts`, `BrokerBackend.registerOutputSubscriber`). Subscription failure must notify the owner and close the viewer rather than strand an open socket with no output.
4. Browser `public/pty-socket-client.ts` separately tracks attach acknowledgement, prefill completion, protocol readiness, ordered-resize barriers, and reconnect generations. Acknowledged attach is not a ready terminal. It buffers or streams prefill according to mode, waits for authoritative completion, and closes/reconnects on protocol timeout instead of revealing partial state. Resize IDs/acknowledgements order geometry and deferred output; hydration reveal additionally waits for rendering/layout conditions (`public/{ordered-resize,terminal-hydration,terminal-resize-lifecycle,pty-terminal-controller}.ts`).

**Viewer ownership and transport credit are separate state machines.** `activePtySessions` permits an owner and a pending challenger, not two active input owners. Explicit takeover displaces the old owner and creates a fresh attach; pending viewers cannot send PTY bytes. Teardown releases subscriptions/viewers, not the broker session itself (`src/server/websocket.ts:437–621`). Parked desktop terminals still hold sockets and ownership; pool expiry/hidden-page eviction bounds that invisible claim. Pool keys include machine plus session (`public/terminal-pool.ts`, orchestration in `public/app.ts`). Grid/manual/delegation workspaces also have separate lifecycle state and must not be merged by name alone.

Output coalescing must retain FIFO order while respecting cumulative viewer credit. Browser ACKs account receipt before prefill/resize buffering, not final canvas paint, and must not be counted again when barriers replay frames. Server pending-output bounds close slow viewers for re-snapshot recovery. On PTY exit, stop the producer but keep transport credit alive long enough to drain already queued output; only then close, or hit the fixed drain deadline. Ring replay truncation forces re-snapshot; prolonged broker loss has a separate reconnect cause. Read both `src/server/websocket.ts:subscribeWithCoalescing` and `public/pty-socket-client.ts:receiveOutputBytes` for any flow-control change. Exact capabilities, close semantics, limits, and deadlines live in `src/{pty-websocket-contract,ws-constants,terminal-prefill}.ts`, not this document.

Wire sequences are binary `bigint`/decimal-string watermarks, not arbitrary JS numbers. `src/broker/codec.ts` owns fragmented-frame buffering, bounded length checks, fatal UTF-8 control decoding, and receiver-owned binary payload copies; `src/broker-output-sequence.ts` and backend snapshot helpers handle representation boundaries. Codec parsing is transport validation, not complete runtime validation of every JSON RPC payload.

## Status, activity, attention, and notifications

Do not conflate broker liveness, raw output watermark changes, rendered activity, semantic agent state, and user acknowledgement. `src/server/agent-status.ts:deriveAgentRuntimeState` gives dead/unavailable broker facts precedence, otherwise chooses eligible fresh semantic sources for the current run, otherwise falls back to rendered activity. Old structured signal sequences cannot roll state backwards; run identity/order and program input-request changes affect transition identity. Acknowledgement covers a transition sequence rather than permanently silencing a session.

`src/server/session-observation.ts` shares canonical state across dashboard and notification observers while keeping cadence-specific fingerprints. Watermarks invalidate snapshots; only changed rendered content establishes activity. A new sample after a capture/liveness continuity break is a baseline, not evidence of activity during the gap. Completed-list ownership and quiet-policy epochs fence asynchronous captures and reductions so an older observation cannot prune or publish over a newer one (`claimObservationAuthority`, `observeSessionFact`, `collectSessionObservation`). Broker unavailable preserves known session projections as unknown rather than falsely turning an empty list into session death.

Quiet-alert policy is reduced server-side, including descendant suppression, and delivery is another layer. `src/server/push.ts:deliverQuietAlert/checkSessionTransitions` freezes recipient enrollment generations per episode, retries only eligible failed recipients, and checks ownership after awaits; new subscribers should not receive historical episodes. Peer observation consumes the remote host's quiet-alert facts rather than re-evaluating its policy locally (`src/server/peer-notifications.ts`). Subscription enrollment/persistence and browser permission toggles are different state; follow `src/server/push-routes.ts`, `public/app-state.ts`, and `src/notification-preference.ts` when touching that boundary. Push encryption/provider behavior was not exhaustively inspected.

SSE is live, in-process, synchronous fan-out with ephemeral event IDs—not task history or a restart-resumable log (`src/server/{event-bus,event-routes}.ts`, `src/events-contract.ts`). Durable task events are published at canonical commit, but subscribing does not recover earlier ledger events.

## Multi-machine routing

Discovery yields candidates, not trusted ready application endpoints. Browser probes verify a machine handshake; stable identity combines Tailnet node identity with installation identity. Display names and old persisted origins do not grant routing authority. `src/tailnet-peer-registry.ts` retains unavailable metadata without making it routable; `public/app.ts:refreshTailnetPeers/retireReplacedPeerIdentity` invalidates stale refresh work and retires affected terminals/workspaces when the installation changes. Session refresh and socket connection callbacks carry their own generations—do not assume a single page-global generation covers every async path.

Most session traffic connects directly from the browser to a currently ready peer; CLI `--machine` resolves a canonical hostname within configured Tailnet namespace and validates its handshake before supported remote commands (`src/cli/machine-target.ts`). Selected-host extensions instead use the local server's constrained read proxy below. Relay federation uses yet another host-owned topology/epoch verification path. Avoid treating all three as a generic arbitrary-URL proxy. Canonical origins, handshake compatibility, and capability policy are authoritative in `src/tailnet-machine-contract.ts`; installation persistence is `src/tailnet-machine-installation.ts`.

## Extensions: trusted code, constrained data channels

**Installed UI code is trusted page code, not sandboxed code.** Server installation never imports package JavaScript. Exact npm acquisition or absolute local directories become private immutable inventory-digested snapshots, declarations/schema are checked before registry commit, and package identity owns the extension ID. Read `src/extensions/runtime.ts` with `package-security.ts`, `archive-snapshot.ts`, and `registry-acquisition.ts` for acquisition/cleanup. Registry claims alone do not authorize bytes: registry loading rechecks owned snapshots and manifest coherence. A directory lock serializes registry transactions and deliberately has no automatic stale-lock recovery. Schema-changing updates are rejected rather than silently migrated. Skill deployment follows registry commit and is not the same atomic transaction.

- Public authoring API source is `src/extensions/public-sdk.ts`; checked-in `sdk/extensions.js` and declarations are emitted by `scripts/build-extension-sdk.ts`. Runtime/host contracts are broader than the published surface. SDK generation is not an npm-install lifecycle step.
- Local asset delivery permits only declared UI bytes for an enabled, digest-matching installation (`src/server/extension-routes.ts`, `ExtensionRuntime.asset`). Browser loader requires a bounded, authenticated, same-origin, nonredirected JavaScript response, verifies its digest, rechecks scope before Blob import, then revokes the Blob URL. Acquisition/evaluation deadlines are not equivalent: JavaScript already evaluating cannot be cancelled (`public/extension-loader.ts`). Self-contained ESM is therefore an extension compatibility requirement.
- Scope includes installation, extension, session UUID, and machine routing identity. Host generation/abort checks fence catalog acquisition, registration, view ownership, and polling; hiding an individual context view must not keep another document key polling (`public/{extension-host,extension-document-polling,extension-scope,context-view-registry}.ts`). Browser safe mode stops host loading; server safe-mode behavior is a separately injected route-service policy, not automatically the browser preference.
- Documents are bounded canonical JSON with server-installed schemas, per-key revision CAS, and retained request-ID receipts (`src/extensions/document-contract.ts:ExtensionDocumentStore.publish`). Inputs are snapshotted before queueing. Exact retained duplicates are checked before current writable-scope policy; new writes require a live exact broker UUID. Locks/quota atomicity are instance-local, not cross-process coordination. Existing retained documents can be read after session exit; reads do not imply current writable scope.
- Blob content is digest-addressed and installation/extension-owned, not per-session storage. Mutation requires a live exact session and rechecks enabled/package authority after body acquisition; reads have a different scope contract. Git access derives cwd from a live UUID, bounds concurrency, and rechecks UUID/project and package identity after subprocess work (`src/server/extension-routes.ts`).
- Remote extension reads use canonical identity-addressed suffixes, not supplied upstream URLs. `ExtensionPeerProxy` verifies current topology and public handshake before forwarding the separately supplied peer credential, validates enabled inventory before/after the read, checks returned ownership/digest, and re-verifies identity before delivery. Retries restart the whole acquisition under one shared deadline (`src/server/extension-peer-proxy.ts`, `src/extensions/selected-host-contract.ts`). Browser transport separates local auth from peer-auth headers and requires explicit consent for the offered remote executable inventory; inventory/origin changes retire consent (`public/extension-transport.ts`). This is read-only data mediation, not code isolation.

## Durable tasks versus volatile relay / task-worker readiness

There are two task-related systems initialized by the server; do not transpose their guarantees.

**Durable task API:** `src/tasks/gateway.ts`, `domain.ts`, `store.ts`, and `lifecycle.ts` own immutable assignments, participant/event validation, sender-canonical ordering, sender/receiver ledgers, delivery/idempotency, and recovery. JSONL ledger fsync is authoritative; caches/inbox indexes are rebuildable and cache failure cannot negate a committed event. Records with the same identity must have identical canonical content. Delivery sequences have separately durable reservation metadata. Startup reconstructs ledgers, quarantines invalid complete records, and can represent an uncommitted final fragment without allowing further append to that ledger. Lifecycle timeout/retention is swept at startup/access, not by an implicit scheduler; unfinished/unacknowledged ledgers do not simply age out. Read store fault-injection tests for crash-ordering changes. Durable peer delivery has its own auth limitations in `TaskGateway.send`—not the volatile federation policy.

**Volatile relay:** `src/task-relay/gateway.ts` accepts only the current memory-owned profile; retired profiles are errors. `WorkerRelayGateway` owns one worker per normalized root and budgets requests, transferred bytes, callback concurrency, and response time. Main-thread callbacks retain broker inspection/network authority. Worker isolation is not a security boundary. Timeout/failure closes the worker and rejects outstanding work; a mutation may already have committed. Replacement must await confirmed termination, and normal recovery is explicit endpoint rebind after epoch loss, not automatic replay (`src/task-relay/worker-client.ts`).

`VolatileRelayGateway` and `MemoryRelayStore` hold epoch-bound endpoint generations, leases, mailboxes/receipts, and forwarding state in memory. No disk spool/history is implied by the root argument; optional investigation diagnostics are not recovery authority. Endpoint retry drives forwarding, and uncertain delivery has explicit state. Suspension-inclusive maintenance compensates live registration leases across material timer gaps without moving relay deadlines (`src/task-relay/{volatile-gateway,memory-store,suspension-inclusive-clock}.ts`). Read those sources for exact capacities/lease/expiry semantics.

Volatile HTTP ingress has its own bounded body/deadline and trusted-client policy in addition to the shared HTTP middleware (`src/server/volatile-relay-routes.ts`). Federation assumes honest canonical TLS/Tailnet peers and ACLs, not signed task principals. Local topology and both epochs are checked around forwarding; endpoint-selected arbitrary origins are not authority (`src/task-relay/peer-transport.ts`, `src/server/relay-peer-transport.ts`). Do not deploy those loopback/forwarded-address assumptions behind an untrusted proxy.

**Task-worker ready means more than “process exists.”** Target-host preflight resolves readable executable/extension resources and layered host → canonical-project → spawn policy, keeping mandatory task support and validated environment/options (`src/server/{task-worker-policy,task-worker-readiness}.ts`). Readiness repeatedly proves the created UUID, canonical project, Pi harness, liveness, and a compatible live relay registration; it rechecks both identity and registration before returning. Failure attempts bounded exact-UUID kill and reports whether cleanup was confirmed. A ready response does not guarantee later lease continuity. Test/source truth for these orderings: `tests/unit/task-worker-readiness.test.ts`, `tests/integration/selected-host-startup-ownership.test.ts`, and task-worker E2E fixtures.

## Generated artifacts, native coupling, and verification routing

- Browser changes must flow through `scripts/bundle-app.ts` / `bundle-ghostty.ts` → `scripts/gen-assets.ts` → `src/public-assets.ts`. The server serves the embedded map, not the live `public/` directory. Editing TypeScript or CSS alone need not change what an existing fixture/binary serves. Per-asset hashes control immutable caching; HTML gets a per-response CSP nonce. PWA service worker bypasses API/WebSocket/non-GET authority traffic and caches shell assets, not API authority (`src/server/http.ts:serveHtml/serveFile`, `public/sw.js`). Do not debug a stale binary by editing its generated embedded module directly.
- Browser Ghostty and daemon native Ghostty are separate build paths. The browser shim caches compiled WASM modules but creates isolated instance/memory per terminal because upstream singleton memory is unsuitable for concurrent cells (`scripts/bundle-ghostty.ts`). `package.json`/`bun.lock` apply `patches/ghostty-web@0.4.0.patch`; rendering, resize presentation, synchronization, and listener cleanup tests depend on the patched package, not stock upstream behavior. Prewarm is about instance lifecycle, not sharing terminal state.
- Native integration is pinned by `ghostty-vt.lock.json` and authenticated patch digests; `scripts/build-ghostty-vt.ts` re-extracts authenticated source, applies patches without fuzz, and checks actual archive symbol readability and host-libc symbol policy when building. These checks prevent a native library from substituting process-wide memory routines; merely having an archive/manifest is not equivalent verification. Daemon-side native source remains a sibling read boundary.
- `scripts/build.ts` requires explicit build mode. Local mode builds/stages a fresh host broker; package-all validates release broker artifacts against target/version/revision/hash and source cleanliness before packaging; server-only compilation is not a full deployable-pair proof. The relay worker is an explicit named compile entry, so source-mode success alone does not establish packaged worker resolution. Artifact and version authority is in `scripts/{broker-artifacts,release-version-policy,publish-policy}.ts`. Installer verifies both downloaded payload checksums before invoking the staged server's pair-install owner (`install.sh`, `src/cli/service.ts`); no whole-install rollback guarantee was established here.
- HTTP/WebSocket schema source is `src/control-api/schema.ts` with shared contract imports; runtime validation remains in handlers/helpers, not an automatic schema middleware. `scripts/gen-control-api-schema.ts` emits documentation outside this module's source scope. Contract tests compare these representations. Exact request fields, message maps, limits, and enum values belong in those sources, not in this context.

Verification choices:

- `bunfig.toml` selects Bun unit/integration/snapshot tests, excluding Playwright specs by default. `tests/test-preload.ts` isolates relay storage but does **not** globally set every production singleton into test mode. Set isolation environment before module import; use existing fixture/reset APIs. `createServerInstance()` isolates listeners/WebSocketServer, not all module-level state or quota maps. Importing production server code without `WOLFPACK_TEST` can auto-start/connect to the real environment.
- Root typecheck is strict, browser compatibility typecheck is not fully strict, and `public/tsconfig.strict.json` covers selected migrated paths. A passing browser compatibility check does not imply every browser source has strict coverage.
- Default E2E harness uses a mock backend and re-execs with isolated HOME because Bun caches homedir at process start (`tests/e2e/test-server.ts`). Real terminal/restart/takeover behavior needs `broker-helpers.ts` and `test-server-broker.ts`, which probe a real private broker socket before READY. The short `/tmp` socket root is intentional for platform pathname limits. Mock success is not native/protocol verification.
- For attach/resize/credit changes pair unit tests such as `broker-ws-attach`, `pty-socket-client`, and `ordered-resize` with real-broker integration/E2E tests; for extension scope/transaction changes use extension runtime/document/peer-proxy tests plus compiled-host fixtures; for relay ownership changes use packaged/compiled-worker integration tests, not just source tests. Build generation and native toolchains can write substantial artifacts; do not run release/deploy/install scripts as ordinary checks.

## Evidence limits

This large-module pass traced the authority and ordering boundaries above, not every UI action, native dependency, push cryptographic primitive, CLI command, archive-parser branch, or durable-task peer/recovery branch. Sibling daemon behavior and external Tailscale/service-manager/push-provider semantics remain external contracts. Generated bundle bodies and executable payloads were not treated as source authority. Octocode structure output was initially paginated; native file enumeration and exact bounded source reads supplied routing evidence, with no whole-repository semantic/dead-code claim.

A write-free Bun 1.4.2 assertion probe passed for ambiguous name/UUID rejection, UUID selector resolution, fragmented binary-frame round-trip with a sequence beyond JS safe-integer range, and one-use ticket consumption after wrong-client presentation. No full Bun suite, browser suite, native build, service activation, or release smoke was run; test pointers above are routing guidance, not a claim those suites passed in this pass.
