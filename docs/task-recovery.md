# relay restart recovery with live task clients

status: draft, pending independent review and final integration gates. no installed-service or deployment claim.

## scope and compatibility

server/relay restart recovery preserves opaque mail and transport progression while the **same plugin/agent processes stay alive**. plugins retain semantic task state, presentation evidence and pending outbox in RAM. this is at-least-once transport with stable protocol IDs, not exactly-once model/tool execution.

existing clients keep `volatile-v1`, `/api/task-relay/volatile-v1`, `/peer`, `/resolve-peer` and envelope protocol version 2. the historical wire name does not select storage. callers may use the existing name-or-UUID selector; fresh broker inspection resolves it to the canonical session UUID, which owns the registration. a reused name cannot access a different UUID's endpoint. clients never supply a recovered receive cursor or synthesize an endpoint.

server storage defaults to native SQLite. `WOLFPACK_TASK_RELAY_STORAGE=memory` explicitly selects the old weaker RAM-only server behavior; `WOLFPACK_TASK_RELAY_PROFILE` still accepts only `volatile-v1`. profile metadata identifies the store epoch and wire interface, not endpoint persistence, task readiness or execution. the removed WIP `restart-safe-v1` wire profile is not required or advertised. there is no automatic empty-store fallback.

baseline RAM-only clients can use the new server without upgrading. the focused client change adds truthful typed storage errors and cooldown diagnostics. new clients still speak to old servers; an old server restart still loses its epoch/mail and triggers the baseline truthful lost-state/rebind behavior.

plugin/agent-process restart recovery is **not implemented**. no endpoint SQLite/task journal, conversation/file identity bootstrap, transcript fsync, persistent presentation reservations, new Claude interrupted-MCP policy or endpoint-history garbage-collection protocol is included. session history does not restore active tasks or authorize replay.

## storage and retention

- the worker exclusively owns `restart-safe-v1.sqlite` under the configured relay root (normally `${WOLFPACK_DIR:-~/.wolfpack}/task-relay`). this is an internal storage filename/format, not wire negotiation. format `wolfpack-relay/restart-safe-v1`, SQLite `user_version=1`; no legacy data is read, migrated or deleted.
- owner-private directories (0700), files (0600), ownership, regular-file, hardlink and sidecar checks precede opening. SQLite EXCLUSIVE locking prevents concurrent owners. DELETE journals and FULL synchronization commit primary changes before acceptance/ACK responses or external forwarding.
- virgin SQLite initialization uses a reserved `.initializing` slot and native exclusive ownership, then atomic no-replace link/unlink publication plus directory fsync. a killed creation may resume only that unpublished slot or an exact owner-private, same-inode, two-link publication pair with valid format/origin and zero primary cells. arbitrary empty final files, corrupt slots and non-virgin hardlinks remain invalid and unchanged. the final connection reopens after link-count repair before any primary writes.
- primary state includes epoch, canonical session/generation registrations and their current/noncurrent status, endpoint cursors, peer aliases/epochs, receipts, immutable envelopes and forwarding progression. derived indexes rebuild after format/origin, integrity, checksums, relationship and bounded-usage validation. corrupt or unverifiable state blocks recovery instead of creating an empty epoch.
- reopening drops obsolete in-flight forwarding tokens, not immutable envelope/dedup identities. only the live endpoint reoffering its original operation drives another attempt; the owner never replays an interrupted mutation. unknown/rejected/expired forwarding reports uncertainty, not guessed acceptance.
- existing item/byte ceilings remain. new envelope admission has a seven-day horizon; terminal receipt tombstones remain eight days after completion. on receipt eviction, a fixed-size durable cutoff advances to the greatest evicted envelope `createdAt`. unseen envelopes at or below that cutoff fail `ENVELOPE_EXPIRED`, even after wall-clock rollback and reopen. retained receipts and accepted unacknowledged mail bypass new-admission checks; fresh timestamps above the cutoff do not inherit the previously observed wall-clock high. receipt creation timestamps and the cutoff are required recovery state; incomplete older draft journal state fails closed, without migration. accepted unacknowledged mail does not passively expire, but explicit target-lifetime retirement discards it as described below. SQLite page limits bound database growth.
- lease expiry, disconnection and broker unavailability are **not death**. the same current generation renews its existing endpoint/cursor after a lease gap unless a fresh generation or proven-death reclaim has retired it. native reopen preserves the epoch and current generation; live clients do not need to rebind just because the server restarted.
- on registration-capacity pressure, one bounded round-robin probe freshly inspects an expired current registration's exact broker UUID, including registrations with receipt references. only authoritative death or `NOT_FOUND` can retire it. a conditional mutation check rejects a stale proof after concurrent renewal. unavailable, ambiguous or mismatched results retain state. retirement applies the same old-lifetime mail rules as fresh-generation replacement. retained outgoing mail and terminal evidence can still consume capacity; later capacity retries continue probing.
- the first live registration owns a session. an epochless fresh-generation connect with a different generation receives retryable `SESSION_ALREADY_REGISTERED` with `retryAfterMs` equal to the remaining lease. after disconnect or lease expiry, fresh canonical broker inspection permits a new endpoint/cursor0. old mailbox or forwarding obligations no longer cause `RELAY_RESET`.
- retirement forgets unread mail addressed **to** the prior endpoint and pending peer forwarding **from** it, releasing payload, mailbox/peer credits and in-flight tokens. it uses the existing loss/unknown-outcome path, not fabricated delivery or ACK evidence. senders retrying the old target get `TARGET_NOT_REGISTERED`; retired sources cannot act. forgetting advances the existing durable admission cutoff, preventing resurrection of a discarded envelope after reopen. late peer responses cannot recreate a forgotten forwarding receipt; already accepted remote mail is not retracted.
- unread local mail **from** the prior endpoint to another current endpoint stays deliverable and can be acknowledged normally. terminal receipts retain their exact IDs, digests, state, acceptance IDs, expiry and bounded charges. a predecessor with remaining references becomes noncurrent, without endpoint/task/ACK authority; otherwise it is removed. capacity preflight counts both registrations when the predecessor must remain, and failures leave all mail unchanged.
- current/noncurrent identity, generation, retirement and capacity checks occur synchronously in the committed store mutation. restore permits a noncurrent registration as the source of local mailbox mail, never its target or the source of pending peer forwarding. it still rejects multiple current registrations per session and empty retained predecessors. forgetting the last referenced receipt prunes its noncurrent predecessor in the same mutation; current registrations are never swept this way. capacity can still reject a fresh generation explicitly with `RELAY_CAPACITY`. older binaries that reject noncurrent mailbox sources cannot reopen such state; do not downgrade while that state exists.
- stale endpoint send/receive/ACK and retained-generation reactivation fail. normal bound clients include their saved epoch on reconnect; an epoch-bearing connect may only renew the current generation, even after predecessor records expire. an epochless request explicitly declares fresh lifetime semantics; after bounded history pruning, arbitrary reuse of an ancient generation string without a saved binding cannot be distinguished from another deliberate fresh connect. no unbounded generation tombstones or new wire negotiation are added. delayed target inspection revalidates the exact current endpoint/generation before renewal and cannot resurrect a predecessor.
- after normal wire/auth/trusted-peer/origin/epoch validation, an exact terminal receipt with acceptance evidence may confirm a duplicate without making its old target deliverable. immutable envelope digest/endpoints must match. changed, absent or expired receipts cannot admit mail to the old endpoint; terminal unconfirmed forwarding remains unknown without acceptance evidence. the same evidence recheck handles a mailbox ACK/replacement racing with awaited broker inspection.
- starting a fresh empty client is usable after the predecessor disconnects or its lease expires, subject to normal capacity limits, even when old-lifetime mail is unread. this is not recovery of lost plugin RAM: predecessor tasks, outbox, cursors and ACK authority are never adopted. retained outgoing mail remains addressed to its original target; no old task is replayed into the fresh endpoint.

## owner failures

failed owners stop and release their reservation only after confirmed termination. replacement reopens the same journal in single flight, with monotonic cooldowns of 1, 2, 4, 8, 16 and then 30 seconds. no uncertain mutation is replayed. only a successful connect from the current healthy owner resets recovery health; delayed committed replies remain truthful but cannot clear a later failure.

`RELAY_STORAGE_UNCERTAIN` is owner-fatal and potentially committed. `RELAY_STORAGE_BUSY` and `RELAY_STORAGE_UNAVAILABLE` report transient lock/open failures without takeover. `RELAY_STORAGE_INVALID` permanently blocks corrupt/unsupported/unverifiable storage for that facade lifetime. `RELAY_STORAGE_RECOVERY_BLOCKED` keeps the reservation when termination is unconfirmed. `RELAY_STORAGE_RECOVERING` rejects before admission with `retryAfterMs`. none authorizes a fresh task execution, new assignment, empty fallback or cursor resurrection.

## startup containment and capability health

recognized relay owner/startup failures do not prevent HTTP or WebSocket startup. authentication, broker setup, and durable-task initialization retain their existing checks. the default SQLite gateway also contains native worker construction failures. it confirms termination before replacement and applies the existing bounded cooldown; invalid storage remains blocked for that gateway lifetime. startup never repairs rows, renames state, selects empty memory storage, or restarts the broker.

`GET /api/health` keeps its broker-owned `status` and adds a side-effect-free `relay` snapshot:

- `{ "state": "starting" }`: the worker has not reported ready (or the context has not constructed it).
- `{ "state": "ready" }`: the current worker opened its store. this is not endpoint registration, delivery, or task execution proof.
- `{ "state": "unavailable", "code": "RELAY_STORAGE_INVALID", "retryable": false }`: a bounded safe diagnostic. other owner failure codes preserve their retry classification; generic worker failures use `RELAY_UNAVAILABLE`.

core `status: ready` does **not** imply relay readiness. reading health does not create a worker, retry a request, reset state, or replay mail. profile/epoch lookup and relay operations return HTTP 503 on owner failure; registration lookup rejects rather than returning a fabricated endpoint. task-worker readiness still fails closed and performs its existing exact-UUID cleanup. session listing and terminal input remain broker-owned.

`RELAY_STORAGE_INVALID` can mean invalid relationships in otherwise valid SQLite. an `integrity_check` result of `ok` does not establish semantic validity. preserve the original diagnosis; do not infer the writer or state-creation history from receipt timestamps.

the relationship rules changed with the first-owner/retirement release (#484). current builds accept a noncurrent registration as the source of retained local mailbox mail. builds before that change reject the same journal as `RELAY_STORAGE_INVALID`. a noncurrent mailbox target or a noncurrent source of pending peer forwarding is invalid on both sides of that boundary. before diagnosing corruption, record the served build and check which rule set it applies. this compatibility boundary does not identify which binary wrote a journal. it does not authorize a downgrade, row repair, reset or archival; the explicit procedure below still requires separate authorization.

local server logs record the native cause of a relay worker construction/setup failure or worker `error` event once, at the relay worker owner. health and relay HTTP replies carry only the bounded codes above, never the native message.

## explicit operator loss/reset procedure

this procedure requires separate authorization accepting undelivered-message loss and uncertainty about already accepted deliveries. it is not an automatic startup repair. do not perform it merely because a deployment failed.

1. record the authorization, reason, timestamp, host, configured relay root/storage mode, served build identity, broker PID, and existing session UUIDs. collect `/api/health`, `/api/info`, `/api/sessions`, and bounded server diagnostics in a unique owner-private directory (0700; files 0600). record the old epoch only if safely available; otherwise record `unknown`. retain the failed deployment directory separately. do not expose payloads or credentials in shared logs.
2. stop **only** the server/relay owner. on macOS, use the verified `gui/<uid>/com.wolfpack.server` launchd service and its installed plist. verify the exact server process and its owned workers/children have exited and no other process owns the configured relay files. stopping a restart loop, observing a healthy port, or seeing a stale PID is not sufficient ownership evidence. if ownership cannot be confirmed, stop here. never stop/restart `com.wolfpack.broker` for relay recovery.
3. create a unique private archive on the same filesystem. before moving anything, write the explicit loss-acceptance record and intended source/destination paths into it. verify the destination does not exist. move the **whole relay directory**, including SQLite rollback journals, initialization slots, and any other sidecars, intact beneath that archive. preserve diagnostics alongside it. do not delete rows, copy only the main database, overwrite an earlier archive, or weaken validation.
4. if archival fails or ownership is ambiguous, leave the server/relay stopped and the original state untouched. do not create a fresh root over existing evidence. if interrupted after the move, inspect the recorded paths and archive before resuming; do not repeat the move or import the archive. the operator record must remain discoverable even before fresh startup.
5. after successful archival, bootstrap only the verified server service with the original configuration. an absent relay root creates a fresh epoch. independently verify core health, `relay.state: ready`, the served build/asset identity, unchanged broker PID, preserved session UUIDs, and actual terminal attach/input. verify fresh endpoint registration separately; profile metadata alone is insufficient.
6. leave the archive immutable to normal operation. never replay its mail, import its cursors, reissue historical assignments, or treat old endpoint IDs as new authority. a fresh task requires a new explicit assignment.

current Pi and Claude adapters replace an epoch-lost RAM lifetime with a fresh endpoint. active tasks receive explicit local `RELAY_STATE_LOST` records with unknown remote outcome; these are not canonical remote completion or ACK events. old task IDs are unavailable in the fresh lifetime. Claude's buffered loss note appears through its inbox path, not an extra parent wake. adapter-process crashes still lose RAM, and origin-owned deadlines require the owner runtime to survive. unchanged older clients may require their explicit rebind workflow; inspect the installed client rather than assuming all running agents match source.

## failed deployment closeout

`scripts/deploy-local.sh --broker=no` checks core health and relay health separately from served assets, installed artifact identity, broker PID, and preserved sessions. unavailable or missing relay health makes deployment non-success even if terminal access works. no health failure triggers a relay reset or another service restart.

post-mutation failures retain `~/.wolfpack/deploy.lock` and private evidence: owner PID/start/failure times, `deployment.json` with expected build hashes and prior process IDs, available session snapshots, CLI diagnostics, `verification.json` with observed build hashes/process IDs, and `health.json`/`health.stderr` when those checks ran. earlier failures may lack later-stage artifacts; missing evidence is not success. a failed lock is not automatically stale, and another deployment refuses to reuse it.

after separately authorized recovery, verify the current service, served build, both health components, broker continuity, and session identities **without rerunning deployment**. establish that the recorded deployment owner and all its children have exited; account for PID reuse using process identity/start information and saved diagnostics. if owner identity or recovery remains ambiguous, retain the lock. closing it out requires separate explicit authority: write the recovery outcome beside the failure evidence and archive the entire lock directory to a unique private destination without overwriting prior evidence. a later deployment is a separate action, not a way to clear the lock. successful emergency recovery does not retroactively make the original deployment successful.

## trust and verification limits

existing optional global JWT authentication, loopback/trusted Tailnet admission, canonical TLS origins, current topology and both relay epochs still apply. peers are assumed honest canonical machines, not signed task principals. do not expose these APIs through Funnel or an untrusted proxy.

focused tests exercise real server/worker process restart with an unchanged baseline RAM client, lost committed send/ACK responses, a real lease-length gap, stable epoch/endpoint/cursor progression, terminal result then parent ACK, and assignment/wake deduplication. trusted cross-host tests restart one and both actual relay host processes while clients remain alive. the network fixture maps canonical TLS origins to private loopback listeners; it does not claim physical two-host/Tailscale or power-loss coverage. native SQLite faults, exclusive locks, format/corruption refusal and obligation-aware retirement have separate focused checks. mixed-version failure tests select the exact baseline client/new server and new client/exact baseline server: real broker-unavailable errors and injected typed/unknown replies after committed acceptance/ACK retain RAM and stable retry IDs, with one production inbox assignment/wake. the new server also exercises a real native write fault/reopen with those same client objects alive; the memory-only old server cannot exercise that native fault. baseline clients report unfamiliar epochless storage failures as retryable `INVALID_RESPONSE`, not endpoint resets; newer clients retain typed storage diagnostics. final full suites remain parent-coordinated.
